## Problem Statement

Job seekers repeatedly search several boards, reopen stale listings, compare inconsistent salary and location fields, and manually tailor the same resume for each role. Existing job boards optimize listing volume and application throughput. They do not maintain a trustworthy, personalized shortlist that gets measurably better after every decision.

WorkWink continuously collects live roles with Apify, normalizes and deduplicates them, indexes the source evidence in Elasticsearch, and presents a mobile-first swipe feed. Every recommendation explains the evidence behind the score. A right swipe saves the role and immediately changes future ranking. For saved roles, WorkWink creates a grounded application package that the user must approve.

## Demand Evidence

Demand has not been validated with external users yet. The current evidence is the founder's own repeated job-search pain and conviction that fragmented discovery, filtering, and tailoring should be one workflow. This is enough to build for the hackathon, but not enough to claim product-market fit.

## Status Quo

The assumed current workflow is LinkedIn, Indeed, company career pages, and email alerts; browser tabs and spreadsheets for tracking; repeated reading of long descriptions; manual salary and work-mode filtering; and separate AI chats for resume tailoring. The largest waste is evaluating near-duplicate or stale jobs before any application work begins.

## Target User & Narrowest Wedge

Initial user: a US-based technical professional actively searching for software, data, product, or AI roles and willing to upload a resume. The first wedge is not universal career management or automatic application submission. It is a fresh daily shortlist of jobs the user would realistically accept, with explainable fit and one-click preparation of an application package.

## Constraints

- All displayed jobs must come from real Apify runs. No fixtures or demo listings may reach runtime user paths.
- Elasticsearch is the retrieval and relevance engine, using lexical and semantic retrieval plus explicit filters.
- Apify collection runs every six hours and completion is delivered to the application through an authenticated webhook.
- PostgreSQL is the transactional source of truth for accounts, profiles, consent, swipes, saved jobs, ingestion runs, and application packages.
- Scraped text is untrusted input. It never gains tool access and cannot override system instructions.
- Resume and generated application data are private by default, encrypted in transit and at rest, tenant-scoped, auditable, exportable, and deletable.
- Application submission remains human-approved. Browser automation is a later, separately consented feature.
- The hackathon path must be deployable and observable, not a local-only demo.

## Premises

1. The right product is a decision engine, not another searchable job board. The swipe is useful only because it captures preference feedback with almost no friction.
2. Freshness and provenance are product features. Every job needs source URL, collection time, last verification time, and closure state.
3. Match scores must be evidence-backed. A single opaque LLM percentage is not trustworthy enough for a career decision.
4. Personalization must combine resume fit, hard constraints, explicit preferences, and learned swipe signals. Swipe behavior cannot silently override salary, location, authorization, or work-mode requirements.
5. The fastest production path is a modular monolith with a separate worker process. Microservices add operational failure modes before scale requires them.
6. External demand remains unproven. The product must instrument activation, useful-right-swipe rate, saved-to-draft conversion, and return usage from day one.

## Approaches Considered

### Approach A: Harden the existing Node prototype

Replace demo endpoints with live API calls and add a database beside the current vanilla application. This ships fastest but retains weak module boundaries, a hand-built HTTP layer, and UI architecture that will be expensive to evolve.

### Approach B: Production modular monolith

Use a typed Next.js application for the web and API surface, PostgreSQL for transactional state, a PostgreSQL-backed durable worker queue, S3-compatible private object storage for resumes, Elasticsearch for hybrid retrieval, Apify schedules and webhooks for collection, and NVIDIA NIM for grounded application generation. Keep domain modules isolated so high-load ingestion or ranking can later be extracted without rewriting the product.

### Approach C: Event-driven services from day one

Split identity, ingestion, search, ranking, and application generation into separate deployables with a message broker. This is the ideal shape only after independent scaling, team ownership, or compliance boundaries exist. Today it increases deployment, tracing, data-consistency, and incident-response work without improving the hackathon experience.

## Recommended Approach

Approach B. It is the smallest architecture that can honestly support real users after the hackathon. The application and worker deploy independently but share versioned domain packages and one transactional database. Apify owns the six-hour schedule. Its success webhook starts an idempotent import. Elasticsearch stores normalized, provenance-rich job documents and uses `semantic_text` plus lexical retrieval with reciprocal-rank fusion. PostgreSQL records the user-specific state and a versioned explanation snapshot for every recommendation.

Working name: **WorkWink**. Product line: **Swipe into work worth wanting.**

## Delivery Boundaries

### Must prove at the hackathon

1. One production Apify Actor/task collects platform and backend engineering roles on a six-hour schedule.
2. An authenticated completion webhook triggers an idempotent import into canonical PostgreSQL job records and a versioned Elasticsearch read index.
3. A real resume and explicit preferences produce a filtered, explainable Elastic hybrid-search feed.
4. A swipe is persisted synchronously and changes the next retrieval request through a transparent preference-vector update.
5. A saved job produces a human-approved application package whose claims all point to resume evidence.
6. An HTTPS deployment protected by an account allowlist exposes health checks, structured error logging, and a visible ingestion status panel. It is publicly reachable for judging but is not open for public signup.

### Required before inviting outside users

Email verification and recovery, malware scanning, deletion/export self-service, rate limiting, dead-letter replay tooling, backups, alerts, accessibility checks, expanded browser coverage, and legal review of the selected source. Private object storage, user authorization, and the dead-letter queue itself are already required by the hackathon slice.

### Post-hackathon expansion

Additional role families and sources, team/organization accounts, employer workflows, mobile apps, browser-assisted application submission, learned ranking models, and service extraction when measured load requires it.

## End-to-End Contracts

### Onboarding to feed

The allowlisted hackathon user authenticates, uploads one PDF or DOCX file of at most 10 MB, and completes hard constraints plus role preferences. The worker verifies file signature, size, page count, and parse limits before extracting text; antivirus scanning becomes mandatory before outside-user release. It stores the encrypted original privately, stores structured resume evidence in PostgreSQL, and marks the profile ready. The feed endpoint refuses to invent a profile while parsing is incomplete and returns a retryable processing state.

### Apify run to searchable job

Apify owns the UTC `0 */6 * * *` schedule. The webhook includes a high-entropy secret in the URL path and identifies the completed run. Because this is not a payload signature, the API independently fetches that run through the authenticated Apify API and accepts only a successful run owned by the configured Actor/task. It commits the unique run record and PostgreSQL-backed queue job atomically before acknowledging. Replays are no-ops only when the run is already queued, processing, or complete; a failed run can be explicitly retried. The worker fetches all dataset pages using bearer authentication, validates and normalizes every record, upserts canonical jobs in PostgreSQL, records a source snapshot only when normalized content changes, and bulk indexes the successful canonical versions into a versioned Elastic index behind an alias.

PostgreSQL is canonical for job identity, source snapshots, lifecycle, and recovery. Elasticsearch is a rebuildable retrieval projection. A reindex command reads canonical jobs, creates a new index version, verifies counts and sample queries, then atomically moves the read alias.

### Swipe to rerank

The API writes the swipe and updates the user's compact preference state in one PostgreSQL transaction. A right swipe adds a bounded positive affinity and a left swipe adds a smaller negative affinity for the job's normalized title family, skills, industry, company stage, work mode, and compensation band. Those affinities alter application-layer component scores and optional Elastic lexical boosts; they never become hard filters. The response returns the new preference version. The next feed request includes that version and excludes already-seen jobs. There is no asynchronous promise of immediacy: the next request is the consistency boundary.

### Save to application package

A right swipe creates or updates a saved-job record. The user explicitly requests a package. The worker sends only the selected job evidence and the user's structured resume evidence to NVIDIA NIM, validates a strict JSON schema, rejects claims whose cited evidence ID or quoted span does not exist, and persists the prompt/model/schema versions. WorkWink guarantees citations and human approval, not perfect automated semantic entailment: the review UI places every claim beside its supporting resume span and requires approval before export. Failure returns a retryable state and never silently produces filler.

## Ranking Contract

Hard filters run first: work authorization, allowed work modes, excluded locations, minimum known compensation, and closed/stale status. Missing compensation is a separate user preference, never treated as meeting a minimum. Elastic then retrieves candidates with lexical plus `semantic_text` queries and reciprocal-rank fusion. The v1 deterministic presentation score is semantic/resume fit 35%, required-skill coverage 25%, explicit preferences 15%, freshness 15%, and learned affinity 10%. Affinity values are bounded to the learned-affinity component and may contribute query boosts only as tie-breakers. Every result returns its component scores and supporting passages.

Cold start uses only resume evidence and explicit preferences. Resume originals and structured evidence stay in object storage and PostgreSQL; they are never indexed as user documents in Elasticsearch. A minimal redacted profile summary is sent transiently as search query text and is not stored in the job index. Every swipe updates affinities for normalized title family, skills, industry, company stage, work mode, and compensation band. The feed targets 15% exploration candidates; if fewer eligible exploration candidates exist, it fills from the highest-ranked eligible results and reports the actual ratio in telemetry. Behavioral signals can reorder eligible jobs but can never make an ineligible job eligible. Historical recommendation snapshots retain the job version, score-policy version, preference version, and evidence IDs so explanations remain reproducible after reindexing.

Example: `86% match: platform engineering 31/35; required skills 24/25 (Go, Kubernetes, AWS found in resume evidence R3/R7); preferences 13/15 (remote, compensation disclosed); freshness 13/15 (verified 3 hours ago); learned affinity 5/10. Risk: on-call rotation is required and was not specified as acceptable.`

## Operational Definitions

- A duplicate shares a normalized source ID, canonical application URL, or a high-confidence fingerprint of company, normalized title, location, and description. Ambiguous matches remain separate and are observable.
- A job is stale after 48 hours without successful verification. The import worker marks it closed when the Actor reports closed/expired, the same canonical URL is absent from two complete consecutive source runs, or its source-specific expiry passes. Direct page verification is a later source adapter, not implied by v1.
- Imports retry three times with exponential backoff and jitter. Exhausted jobs enter a dead-letter queue with run ID, dataset ID, and redacted error details.
- A useful right swipe is a saved job not undone within 24 hours. Saved-to-draft conversion is the share of saved jobs for which a valid package is requested within seven days.
- Feed target is p95 below 800 ms after profile readiness. Swipe persistence target is p95 below 300 ms. Webhook acknowledgement target is below 2 seconds because import is asynchronous. The release gate measures at least 500 feed requests and 500 swipe writes over a ten-minute load test at 10 concurrent users.
- Initial capacity target is 1,000 users, 250,000 active jobs, and 2 million content-change snapshots without architectural changes. Repeated unchanged observations update verification timestamps without creating snapshots.
- External degradation is explicit: stale-but-labeled feed during an Apify outage; lexical-only retrieval if inference is unavailable; no application package if NVIDIA is unavailable; account creation pauses if email is unavailable; resume upload pauses if object storage is unavailable.

## Privacy and Retention

Resume originals and generated packages are private objects with per-user authorization and short-lived signed downloads. Parsed evidence, swipes, and packages remain until the user deletes them or closes the account. Unverified accounts expire after seven days. Raw source snapshots remain 30 days; normalized job lifecycle data remains 180 days after closure for deduplication and audit. Account deletion immediately revokes sessions and queues deletion of private objects and user-owned PostgreSQL rows; shared canonical jobs and source records remain. There are no user-specific Elasticsearch documents in v1, and deletion verification confirms that no user ID is present in any indexed document. Apify receives only global source configuration, never resumes or user preferences. Elastic receives normalized job data and transient redacted query text. NVIDIA receives only the evidence required for a requested package. These boundaries appear in consent and privacy copy.

## Milestones and Decision Gates

1. **Integration spike, two hours maximum:** evaluate a primary and backup Apify Store Actor/source in the first 30 minutes, then resolve the chosen schema and terms, Elastic inference endpoint, private object store, and NVIDIA structured-output behavior using real credentials. Exit only after one real dataset page is normalized and searchable, one private object passes an authorized upload/download test plus a denied cross-user test, and one schema-valid NIM response is produced. Stop any source path whose terms prohibit intended use; if both candidates fail, the live-data requirement blocks the project before UI work begins.
2. **Data spine, four hours maximum:** canonical schema, Apify webhook/import, lifecycle rules, Elastic index template/alias, and reindex recovery. Exit after replaying one real run twice produces no duplicates and a clean reindex preserves searchable count.
3. **Private user spine, five hours maximum:** allowlisted authentication, private resume upload/parsing, preferences, feed retrieval, swipe persistence, and explanation snapshots. Exit after a real resume reaches a real feed and the next request changes after a swipe.
4. **Action spine, two hours maximum:** saved jobs and evidence-validated application packages. Exit after every generated claim cites an existing evidence ID and exact supporting span; unsupported or mismatched citations fail validation and are regenerated once before surfacing an error.
5. **Release spine, three hours maximum:** HTTPS deployment, secrets, migrations, CI, browser smoke tests, status panel, runbook, and demo script. Exit after a clean environment deploy completes and the demo path plus load-test profile pass.

The initial monthly cost ceiling is $250 across hosting and model/search usage, modeled for 1,000 registered users, 100 daily active users, 20 feed requests per active user per day, 250,000 active jobs refreshed four times daily, and 1,000 generated packages monthly. The integration spike records measured ingest, inference, and generation unit costs; public signup stays disabled if the projection exceeds the ceiling. Rate limits and per-operation cost telemetry make overruns visible.

## Open Questions

- Which Apify Actor or Actor task will be the first production source, and what exact input schema does it require?
- Which Elastic deployment and explicit inference endpoint will be used for `semantic_text`?
- Which production object store and email provider will be used?
- Which NVIDIA NIM model will be selected after evaluating structured-output quality and latency?
- What job-source terms permit storage, display, and refresh at the intended cadence?

These are milestone-one blockers. They are time-boxed to the first implementation slice and cannot be deferred behind UI work.

## Hackathon Success Criteria

- An allowlisted account can authenticate, upload a real PDF or DOCX resume, complete preferences, and receive a feed without code or database intervention during the demo.
- A scheduled Apify run completes every six hours; its dataset is imported idempotently; duplicates merge; missing jobs age out; and failed imports retry with a dead-letter path.
- Every card contains live provenance and an explanation derived from stored evidence. Closed or stale roles are excluded.
- Every swipe is durable, user-scoped, auditable, undoable, and reflected in the next feed request.
- A saved job can produce a schema-valid, evidence-cited resume and cover-letter package through NVIDIA NIM without inventing experience.
- CI runs formatting, static analysis, unit, integration, migration, and browser tests. The deployed service exposes health, readiness, structured logs, metrics, and trace correlation.
- The hackathon demo visibly proves Apify freshness, Elasticsearch retrieval, adaptive ranking, and an actionable approved output.

## Outside-User Release Criteria

- A new user can create an account, verify email, recover access, upload a scanned resume, and receive a feed without administrator intervention.
- Deletion/export, rate limiting, alerting, backups, privacy copy, source legal review, and the expanded security/browser test suites pass their release gates.

## Distribution Plan

Public GitHub repository with a containerized web process and worker process, local Docker Compose for PostgreSQL and S3-compatible storage, and GitHub Actions for checks and container builds. Production secrets stay in the deployment provider. Migrations run as a controlled release step. The public demo is deployed behind HTTPS with seeded configuration but never seeded job or user data.

Confirm the wedge only if at least two independently demonstrate repeated cross-source searching plus a manual shortlist or tailoring step and would replace that workflow with a trustworthy daily shortlist. ## What I noticed about how you think

- You repeated “don't build just a dummy toy” and “no mock data.” That is the correct quality bar for this product because trust collapses if freshness or match evidence is staged.
- You connected the swipe interaction to immediate ranking adaptation, not just visual novelty. That turns the dating metaphor into a data advantage.
- You kept automatic submission behind a later boundary and required approval first. That protects user agency while preserving the longer-term agent vision.
- You want the hackathon build to become a company. The architecture therefore optimizes for a credible first production system, not maximum feature count on demo night.
